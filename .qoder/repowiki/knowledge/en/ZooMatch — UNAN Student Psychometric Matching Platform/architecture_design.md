The repository is split into two cooperating layers: the runtime (Next.js App Router + Supabase client) and the data layer (PostgreSQL migrations + seed + Python/TS generation scripts). The `supabase_migrations` child defines both the v1 single-track schema and the additive v2 multidimensional dual-track schema (romance + friendship), exposing RPCs (`submit_quiz_result`, `compute_dual_matches`, `get_my_matches_v2`, etc.) that the Next.js API routes call via the Supabase service role. The `scripts_and_data` child produces the canonical JSON fixtures under `data/` (archetypes, microtest items, matching thresholds, synthetic profiles) which are imported statically by the TS runtime and also re-seeded into Supabase via `seed.sql` / `seed_v2.sql`. Cross-child contracts are therefore: (1) the SQL migration version numbers and RPC signatures in `supabase/migrations/` are the source of truth for what the API routes expect; (2) the JSON files under `data/` are the single source of truth for psychometric content consumed by both the Python pipeline and the TS matching engine; (3) `.env.example` plus Zod-validated env parsing (`src/lib/env.ts`) is the shared contract between the Next.js server, the Supabase client, and the HMAC-based identity layer. There is no CI or Docker — orchestration happens through npm scripts (`dev`, `build`, `start`, `lint`, `typecheck`, `test`) and a manual `pip install -r requirements.txt` step for the Python data pipeline.
