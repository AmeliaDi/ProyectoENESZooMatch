## Approach

ZooMatch is a Next.js application with two independent dependency stacks:

1. **Node/TypeScript stack** — managed by npm via `package.json` and `package-lock.json`.
2. **Python stack** — used only by data-generation scripts under `scripts/`, managed by pip via `requirements.txt`.

There is no vendoring, no private registry configuration, and no monorepo tooling; each language uses its canonical package manager.

## Key Files

- `package.json` — declares runtime dependencies (`next`, `react`, `@supabase/supabase-js`, `framer-motion`, `recharts`, `zod`) and dev dependencies (`eslint`, `tailwindcss`, `typescript`, `vitest`, `vite`).
- `package-lock.json` — deterministic lockfile generated by npm; all transitive resolutions point at `https://registry.npmjs.org/...` tarballs.
- `requirements.txt` — pins Python packages for the data pipeline scripts.
- `.env.example` — environment template (no secret or registry credentials are committed).

## Versioning Conventions

### Node dependencies (`package.json`)

- Runtime dependencies use caret ranges (e.g. `^16.4.2`, `^19.3.1`, `^4.6.7`), allowing semver-compatible updates.
- Dev dependencies similarly use caret ranges.
- The `engines` field enforces `node >=22.12.0`, so installs on unsupported Node versions fail early.
- No `pnpm-lock.yaml`, `yarn.lock`, or `package-shrinkwrap`; npm is the sole declared resolver.

### Python dependencies (`requirements.txt`)

- Uses lower-bound-only constraints with an upper bound exclusion: `requests>=2.32,<3` and `beautifulsoup4>=4.12,<5`. This allows patch/minor upgrades but blocks major-version bumps.
- No `Pipfile`, `poetry.lock`, or `setup.py` / `pyproject.toml` — plain pip install is the intended workflow.

## Lockfiles and Reproducibility

- `package-lock.json` is committed alongside `package.json`, pinning every transitive dependency to exact versions and SHA-resolved tarball URLs from the public npm registry.
- There is no equivalent lockfile for Python (no `requirements-dev.txt`, no `pip-tools`/`pip-compile` output); reproducibility relies on the `<major` upper bounds in `requirements.txt`.
- The `node_modules/` directory itself is not committed (it appears in the tree as a placeholder; the actual contents are gitignored).

## Private Registries and Vendoring

- No `.npmrc`, `PIP_INDEX_URL`, `PYPI_MIRROR`, `GOOGLE_ARTIFACT_REGISTRY`, or `GITHUB_TOKEN` configuration was found anywhere in the repo.
- All resolved URLs in `package-lock.json` point at `https://registry.npmjs.org/`, confirming usage of the public npm registry only.
- No vendored third-party code exists under `src/`, `lib/`, or `assets/`; all third-party code enters through the package managers.

## Scripts and Toolchain Integration

The `scripts` section of `package.json` wires the dependency-managed tools into standard commands:

- `dev` → `next dev`
- `build` → `next build`
- `start` → `next start`
- `lint` → `eslint .`
- `typecheck` → `tsc --noEmit`
- `test` / `test:watch` → `vitest run` / `vitest`

Python scripts under `scripts/` (`generar_arquetipos.py`, `generar_catalogo_v2.py`, `recopilar_items.py`, `generate-synthetic-profiles.ts`) depend on the packages listed in `requirements.txt`.

## Constraints Observed

- The project is marked `"private": true` in `package.json`, preventing accidental publication to the npm registry.
- Node version is constrained via the `engines` field; CI or local installs on unsupported Node versions will be rejected by npm/yarn/pnpm.
- Python major versions are explicitly blocked via `<3` / `<5` upper bounds in `requirements.txt`, acting as a soft guard against breaking changes.
